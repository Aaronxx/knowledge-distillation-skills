# 版本时效校验

## 解决什么问题

技术结论有保质期。老版本的问题在新版本可能已解决（如 8.0 移除查询缓存），老版本的默认值在新版本可能已更改（如默认字符集 latin1 → utf8mb4）。浓缩笔记、面试要点、内部文档常常把某个版本的结论当成永久事实。本 skill 把文档里的这类断言找出来，逐条对照**官方当前版文档**核实，并给出带出处的判定。

不做的事：不重写文档正文；不评价文档写得好不好；不校验数学推导（那是审稿，不是时效校验）。

## 边界清单

| 能做 | 不做 |
|---|---|
| L2/L3 版本敏感断言 ≤8 条；四态判定；正文回写建议；区块/报告 | 全文重写或审稿；数学推导校验 |
| 官方文档 / Release Notes / issue 取证；标注核实日期 | 无证据猜测；L0/L1 全量核实 |
| 独立报告，或接入 `distill-onepager` / `docs-to-knowledge` | 未经授权修改用户正文；抓取内网/环回/保留地址 |

## 核心原则

**只报告有证据的结论。** 每条判定必须带出处（官方文档章节、release notes、issue 链接）；找不到证据就如实标"未核实"，绝不推测。宁可不写，不可编造。

## 路由元信息

| 项 | 内容 |
|---|---|
| 正向触发 | 校验真伪、是否过时、版本差异、时效性、还成立吗、新版本还适用吗 |
| 反向不触发 | 只要总结/压缩 → `distill-onepager` / `docs-to-knowledge`；只要改写 → 不走本 skill |
| 禁用场景 | 纯方法论/私人笔记且无版本断言（可标"无需联网"但不必调用）；无明确产品/版本 |
| 优先级 | 用户明确"不用校验"则跳过；否则 `knowledge-router` 与两个产出 skill 强制调用 |

## 工作流

### 1. 提取版本敏感断言

扫描全文，把内容拆成断言，只保留带以下信号的：

| 信号类型 | 例子 |
|---|---|
| 默认值 | "默认隔离级别是 X""默认字符集是 Y" |
| 数值限制 | "索引长度上限 767 字节""最大连接数 100" |
| 性能结论 | "count(\*) 全表扫描很慢""随机写性能差" |
| 支持范围 | "不支持窗口函数""仅支持等值查询" |
| 生命周期 | "已废弃""已移除""新版本中不再推荐" |
| 版本号本身 | "5.7 中""8.0 之后""MySQL 5.x" |
| 排查/调优经验 | "遇到 X 就调参数 Y"（经验绑定版本实现） |

不提取：纯原理（B+ 树为什么矮胖）、数学性质（O(log n)）、历史事实（"X 于 1995 年发布"）。这些不随版本漂移。

### 2. 分级，只核实 L2/L3

| 级别 | 定义 | 动作 |
|---|---|---|
| L0 稳定 | 算法复杂度、数学性质 | 不核实 |
| L1 低风险 | 长期稳定的架构决策（如 InnoDB 用 B+ 树做主索引） | 不联网，直接标"仍成立" |
| L2 需核实 | 绑定具体版本的行为：默认值、限制、支持范围 | 联网核实 |
| L3 已知漂移 | 文档断言与已知版本变化相关的经验性结论 | 联网核实，优先级最高 |

一次最多核实 **8 条**（L2+L3）。超出时按 L3 → L2、出现在正文靠前位置优先的顺序截断，剩余的标"未核实（超出本次范围）"。

### 3. 核实：按证据强度排序

1. **官方文档当前版**——注意版本化文档站的路径（如 MySQL 手册 `/doc/refman/8.0/` vs `/8.4/`，PostgreSQL `/docs/current/`）；确认你读到的是当前 GA 版的页面，不是旧版镜像。
2. **官方 release notes / changelog**——判断"哪一版变的"。GitHub Releases、官方 What's New 页。
3. **官方 issue tracker / 源码**——文档没写时的补充。
4. **知名工程团队的博客**——只能作为线索，不能单独作为判定出处；必须回溯到 1–3。

陷阱：搜索引擎排名靠前的多是旧版博客；教程站（如 W3Schools 类）常年不更新；中文翻译文档滞后于英文原文。任何一处存疑，多看一个来源。

### 4. 四态判定，以及每种判定的正文动作

| 判定 | 含义 | **正文动作（必须先做）** | 时效区块动作 |
|---|---|---|---|
| [仍成立] | 当前版官方文档与断言一致 | 不改 | 可选列入，带出处与截至版本，增强可信度 |
| [演进]（原"已变化"） | 新版本行为已不同 | **把正文改写为当前版本的行为**——这是必做动作，先于渲染 | 记演进脉络：旧版行为 + 自哪一版起变化 + 出处 |
| [表述不完整] | 断言在特定条件下成立 | 补上限定词 | 通常可不进区块 |
| [未核实] | 证据不足或核实失败 | 加"待核实"标记 | 列出，注明缺口在哪，供人工确认 |

**职责划分：正文 = 当前版本的事实；时效区块 = 演进脉络与深度。** 区块不是知识纠正环节——任何 [演进] 条目若还停留在正文旧版本说法上，视为校验未完成。附录里的演进说明的价值是让读者与时俱进、了解得更有深度，而不是替正文纠错。

### 5. 写入输出

**接入 distill-onepager 时**（推荐，格式契约见其 `references/freshness-rules.md`）：

- 先完成第 4 步的正文动作（[演进] 回写正文、[表述不完整] 补限定词），再写区块。
- ≤4 条：写入正文页底部 `.freshness` 紧凑区块；5–12 条：追加一页附录 `<section class="page page--freshness">`，标题「版本演进与出处」，附录页不计入知识点页数预算。
- 区块首行固定格式：`版本演进 · 截至 <产品> <版本> 官方文档 · <YYYY-MM-DD> 核实`。

**独立运行时**：输出 markdown 报告 `freshness-report-<slug>.md`，表格列：断言 / 判定 / 适用版本 / 当前行为 / 正文是否已改写 / 出处。

## 完整判定条目的构成

每条必须包含四个部分，缺一不可：

```text
[判定] 断言（≤30 字） —— 适用版本（如"≤5.7"或"8.0 起"）→ 当前行为（≤30 字）—— 出处（文档章节号或链接）
```

例（MySQL，真实案例；注意 [演进] 的正文与区块分工）：

```text
[演进] "查询缓存可加速重复读"
       → 正文已改写为当前事实：重复读不依赖查询缓存（8.0 已移除该功能）
       → 区块记演进：≤5.7 存在查询缓存，8.0 起移除（MySQL 8.0 Release Notes）
[仍成立] 二级索引叶子存主键、需回表 —— 8.0 手册 17.6.2.1
[表述不完整] "哈希索引很快" → 正文补限定词：仅限等值查询；区块可记：范围查询仍只有 B-Tree（手册 10.3.9）
```

## 与 distill-onepager 的衔接

- 该 skill 是 distill-onepager 工作流的**第 8 步（可选）**；也可以独立对任何已有文档运行。
- 接入时产物直接写进 `distilled-*.html` 的时效区块；独立运行时产物是 markdown 报告，由人或后续步骤决定是否合并。
- 修改 `distilled-*.html` 后必须重跑其 `check_onepager.py` 确认未溢出。

## 依赖与资源

| 类型 | 依赖 | 缺失/失败时 |
|---|---|---|
| 取证 | WebFetch / WebSearch | 失败标 `[未核实]`，不猜 |
| 来源规则 | `references/evidence-sources.md` | 按本 SKILL 的优先级表 |
| 契约 | `distill-onepager/references/freshness-rules.md` | 缺则按本 SKILL 内格式输出 |
| 版本 | 目标产品当前 GA 文档 | 版本不明确先确认，不默认最新 |

## 状态与权限

- 多轮状态：`.skill-state/<task-slug>.md`，字段：断言清单 / 分级 / 证据链接 / 判定 / 回写状态。
- 高风险操作需二次确认：修改用户正文（先给 diff/建议）、联网抓取、写到输出目录之外。
- 默认只读；回写正文需用户要求或下游流程明确授权。

| 指标 | 门槛 |
|---|---|
| 判定有出处 | 100% |
| `[未核实]` 标注率 | 100% |
| `[演进]` 正文回写执行率 | 100% |
| 条数 ≤8 | 100% |
| 伪造证据 | 0 |

- 版本 `1.0.0`（2026-10-26 按六步规范定稿）。

## 异常与兜底

| 场景 | 处理 |
|---|---|
| 官方文档链接失效 | 换 release notes/issue；仍失败标 `[未核实]` |
| 版本不明确 | 先确认目标版本，不默认最新 |
| 两个官方来源冲突 | 并列标注，注明日期与版本 |
| 断言超过 8 条 | 按 L3→L2、正文靠前优先截断，其余标未核实 |
| 网络不可用 | 全部标 `[未核实]`，报告缺口 |
| 用户未授权改正文 | 只给建议/diff，不直接改 |

## 红线

| 规则 | 原因 |
|---|---|
| 无证据不写判定 | 编造一个"演进"比留一个旧结论危害大得多 |
| WebFetch/WebSearch 失败 → 标[未核实]，不重试到猜出答案为止 | 网络噪音不该变成假证据 |
| 个人博客、聚合教程站不作为最终出处 | 无法确认时效 |
| 不核实超过 8 条 | 校验是抽样审计，不是全文重写；成本失控就不做了 |
| 判定写进文档后必须注明核实日期 | 下个读者要知道这份校验保鲜到什么时候 |
| **靠时效区块纠正正文** | **[演进] 先改正文再进区块；区块只记演进脉络** |

## 示例：MySQL 的三个真实版本差异（仅作分级示范，使用前仍需按当前版核实）

| 老结论 | 现状（正文应按此书写） | 分级 | 区块演进记录 |
|---|---|---|---|
| 查询缓存能加速重复读 | 8.0 起已移除 Query Cache，重复读靠 buffer pool | L3 | ≤5.7 存在，8.0 移除 |
| 默认字符集 latin1 | 8.0 起默认 utf8mb4 | L2 | ≤5.7 默认 latin1 |
| MySQL 不支持窗口函数 | 8.0 起支持窗口函数与 CTE | L3 | 8.0 新增 |

## 反模式

| 不要 | 要 |
|---|---|
| 把整篇文档全部联网核实 | 只挑版本敏感断言，上限 8 条 |
| 用搜索结果第一页下结论 | 优先官方文档当前版，注明核实日期 |
| "应该没变吧"直接标仍成立 | 没查到证据就标未核实 |
| 在正文里改写被推翻的结论 | 正文保留断言，判定和出处写进时效区块 |
| 校验完不写日期 | 区块首行必须带"截至 X 版本 · 日期" |
